== Architekturziele
.Als Ansatz wurden folgende Kriterien besonders hervorgehoben, um unsere Architektur sicher und wartbar zu machen:
* Sicherheit: Da viele User unser Produkt benutzen werden, ist es von nöten, dass man als Aussenstehender keinen Zugriff auf persönliche Informationen erhält. Darunter zählt auch das Kaufverhalten der Nutzer, welches sich durch unsere App ableiten lassen kann.
* Offline-Funktionalität: Unser Produkt soll zwar schnell synchronisierbar sein, um den Austausch innerhalb einer WG gewährleisten zu können, jedoch benötigt man (leider) auch eine Offline-Funktionalität für den Einkaufsprozess. Da in Deutschland die Netzabdeckung als auch die Verbindungsqualität eher schwach ist, kann es daher vorkommen, dass man in Einkaufszentren keinerlei Netz hat, um sich dort die Einkaufsliste der WG abzufragen.
* Wartbarkeit: Durch ein hohes Kundenaufkommen ist es sehr wahrscheinlich, dass sich schnell Bugs als auch Feature-Wünsche äußern werden. Vorallem auf den Aspekt Features müssen wir gewährleisten, dass der Code strukturiert und wartbar ist. Nur so können wir in einer wachsenden Branche dafür sorgen, dass unser Produkt stets das beste Produkt ist.
* Hardware unabhängig: Als Vertriebler können wir nicht sagen, mit welcher Hardware die Nutzer unser Produkt verwenden wollen. Daher ist es wichtig dass wir unser Produkt so aufbauen, dass es nicht zu rechenaufwändig ist und die Logik eher auf unseren Servern gehostet wird.

=== Einkaufslistenbearbeitung über Diffs
Einkaufslisten werden bearbeitet, indem nicht der neue Zustand geschickt wird, sondern was wie verändert wurde. Dies hat mehrere Gründe:

- für die meisten Änderungen ist der genaue Zustand der Liste wenig relevant. Wenn etwas benötigt wird, wird es mit auf die Liste geschrieben (sofern nicht schon vorhanden, dies müsste der Nutzer jedoch in jedem Fall prüfen), und wenn etwas gekauft wurde, kann die entsprechende Menge abgehakt werden. Dafür ist es jeweils nicht nötig, den genauen neuen Zustand direkt zu schreiben, da der Nutzer jeweils nur die Änderungen sicher kennt, die er vornehmen möchte.
- abgesehen von potentiell negativen Anzahlen ist so keine Synchronisierung der Clients nötig, ohne welche es sonst zum Lost Update kommen könnte (eine alternative, deutlich sinnvollere Lösung wäre hier, dass die Clients immer einen Zeitstempel des letzten ihnen bekannten Zustands mit schicken, woraus die Differenzen berechnet werden können, was jedoch unnötig kompliziert ist).
- für den Offlinemodus können so einfach alle Änderungen aufgezeichnet und später abgeschickt werden
- für den Audit Log einer Liste müssen Diffs ebenfalls nicht extra berechnen werden, was den Code vereinfacht
- Diff-Berechnung auf den Client ist simpler, da dieser nur einen möglichen Zustand zum Vergleichen hat
